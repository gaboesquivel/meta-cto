# Pilot data

The files the Pilot Workspace is loaded from (spec 003, decision 0003). The JSON files in this
folder are **empty templates**: they document the format and stay empty. The filled files hold
the Answer Key, so they live in a **private folder outside the repository** (spec 004, decision 0004) and are never committed. A test (`lib/pilot-load/templates.test.ts`) fails if a template
here gains content.

## Private folder

Set `SIGNAL_PRIVATE_DATA_DIR` (shell or `.env.local`) to a folder outside the repository:

```text
$SIGNAL_PRIVATE_DATA_DIR/
  pilot/manifest.json  backlog.json  feedback.json  answer-key.json
  evals/held-out-v2.json        (Held-Out Set v2 pairs; see evals/signal-verdict/README.md)
```

Start by copying the templates (`cp data/pilot/{manifest,backlog,feedback,answer-key}.json
"$SIGNAL_PRIVATE_DATA_DIR/pilot/"`) and fill them there. The commands refuse, and say why, when
the variable is unset, the folder or a file is missing, or the folder resolves (after symlinks)
inside the git working tree (`git rev-parse --show-toplevel`). Only the lock is written back into
this folder. Each Operator keeps their own copy; the committed fingerprint proves it is the same.

| File              | Holds                                                                    |
| ----------------- | ------------------------------------------------------------------------ |
| `manifest.json`   | Who wrote what, which models, and the expected backlog duplicate rate    |
| `backlog.json`    | Accounts and pre-pilot Feature Requests, loaded into the Pilot Workspace |
| `feedback.json`   | Customer feedback items agents file through Checks; never loaded as rows |
| `answer-key.json` | A confirmed `needId` per backlog request and per feedback item           |
| `pilot.lock.json` | Written by `freeze` here: fingerprint, time, counts. Committed.          |

## Rules

1. **Separate people.** The person who confirms Answer Key labels is not the backlog author
   (`manifest.backlogAuthor`). `freeze` refuses an entry confirmed by the author.
2. **Separate model families.** Feedback is generated by a different model family than the
   judge (`manifest.feedbackGenerator.family` versus `manifest.judgeFamily`). `freeze` refuses a
   match.
3. **Stated before the run.** `expectedBacklogDuplicateRate` (0–1) and `statedAt` are set before
   freezing; they are part of the fingerprint.
4. **Confirmed by a person.** Every Answer Key entry, backlog and feedback alike, carries
   `confirmedBy` and `confirmedAt`.
5. **Never committed.** Filled files stay in the private folder; only `pilot.lock.json` is
   committed. Never copy filled content into this folder.
6. **Frozen before the run.** Once frozen, any change to these files resets the reading: `load`
   and `check` report "changed after freeze: reading reset". To start over, delete
   `pilot.lock.json` deliberately and say so in the Proof Report.

## Formats

`manifest.json`

```json
{
  "backlogAuthor": "name of the person who wrote backlog and feedback",
  "expectedBacklogDuplicateRate": 0.15,
  "feedbackGenerator": { "family": "model family", "model": "model id" },
  "judgeFamily": "the judge's model family",
  "statedAt": "2026-11-01"
}
```

`backlog.json`: keys are stable and unique; `account` names an account key. Rows load with
Origin `seed` under the seed key `pilot:<key>`, so backlog metrics treat them as the Pilot
Workspace's pre-Signal backlog.

```json
{
  "accounts": [
    {
      "key": "acme",
      "name": "Acme Diner",
      "plan": "Pro",
      "segment": "restaurant",
      "size": "3 locations"
    }
  ],
  "featureRequests": [
    {
      "key": "fr-swap",
      "account": "acme",
      "actor": { "name": "Sam (CSM)", "type": "staff" },
      "requester": { "name": "Lee", "role": "GM" },
      "title": "Shift swaps in the app",
      "description": "Staff want to swap shifts without calling the manager.",
      "underlyingNeed": "Staff cover their own shifts"
    }
  ]
}
```

`feedback.json`: what an agent files for a simulated customer; `account` names a backlog account.

```json
[
  {
    "key": "fb-1",
    "account": "acme",
    "customer": { "name": "Ana", "role": "Shift lead" },
    "title": "Trade shifts",
    "description": "Let my team trade shifts themselves."
  }
]
```

`answer-key.json`: need clusters. Exactly one entry per backlog Feature Request and one per
feedback item, each with a `needId` (any stable label, such as `swap`). Two items share a need
iff their `needId`s are equal, so feedback can share a need with the backlog, with other feedback
(an intake duplicate inside the pilot), or with nothing.

```json
{
  "featureRequests": [
    {
      "featureRequest": "fr-swap",
      "needId": "swap",
      "confirmedBy": "Rosa",
      "confirmedAt": "2026-11-02"
    }
  ],
  "feedback": [
    { "feedback": "fb-1", "needId": "swap", "confirmedBy": "Rosa", "confirmedAt": "2026-11-02" },
    { "feedback": "fb-2", "needId": "export", "confirmedBy": "Rosa", "confirmedAt": "2026-11-02" },
    { "feedback": "fb-3", "needId": "export", "confirmedBy": "Rosa", "confirmedAt": "2026-11-02" }
  ]
}
```

`check` and the lock count `sharesNeed`: feedback items whose `needId` a backlog request also has.
The expected backlog duplicate rate stays in `manifest.json`.

## Agent harness: linking filings to feedback items

Agents file each feedback item through a Check with the Pilot Key. To score Agent Correctness,
pass the feedback item `key` as the optional `feedbackItemId` on `check_feature_request` (or
`POST /api/checks`), then pass that Check's `checkId` on the Support, Comment or create that
follows. A filing without a `checkId`, or whose Check has no `feedbackItemId`, counts as
unlinked and is not scored.

```json
{
  "actor": { "name": "pilot-agent-1", "type": "agent" },
  "draft": { "title": "Trade shifts", "description": "Let my team trade shifts themselves." },
  "feedbackItemId": "fb-1",
  "onBehalfOf": { "account": { "name": "Acme Diner" } }
}
```

Scoring (`lib/signal/service/answer-key.ts`). A request filed in the pilot has the `needId` of
the feedback item that created it.

- **Support or Comment:** correct when the target request has the item's `needId`, harm when it
  has another; unresolved (counted, not scored) when the target's need is unknown.
- **Create:** a miss when a request with the same `needId` already existed (backlog or filed
  earlier in the pilot), otherwise correct.
- **Product Manager agreement** (blind and non-blind apart): a Duplicate agrees when the other
  side has the same `needId`; Related, Distinct or No Duplicates agrees when no earlier request
  has the same `needId`.

Unlinked, unmatched and unconfirmed items are counted, not scored.

## Commands (Operator only; never part of a build)

All three read the pilot files from `$SIGNAL_PRIVATE_DATA_DIR/pilot` and the lock from here.

- `pnpm signal:pilot:check` — counts, unconfirmed entries, frozen or changed. No database.
- `pnpm signal:pilot:freeze` — writes `data/pilot/pilot.lock.json` once the files are valid and
  every entry is confirmed. Commit the lock before the run; `git status` should show nothing else.
- `pnpm signal:pilot:load` — loads accounts and backlog into the Pilot Workspace on
  `DATABASE_URL`. Idempotent: inserts missing rows by seed key, never overwrites an existing row,
  never touches the Crewday Demo Workspace, and refuses files changed after freeze.

Code: `lib/pilot-load` (`readPilotFiles`, `fingerprint`, `checkPilotReady`, `answerKeyFor`,
`freezePilot`, `loadPilot`; `privateDataDir`, `resolvePrivateDataDir` in `private-dir.ts`).
