## Problem Statement

Signal's bet is that a verdict before every create stops duplicate Feature Requests at intake. Nobody can yet say whether it does:

- **The main metric has no data.** Production shows no reviewed requests, and the backlog scan was never run there, so the baseline is empty too.
- **The numbers can't be trusted once they arrive.** Every write is flagged demo, and Checks and events record no origin, so pilot use, reviewer smoke tests, seed rows and eval runs all count together.
- **The kill test is a first reading, not a verdict.** The Held-Out Set has 25 pairs with 10 same-need positives (4 of 25 on one target), written and labeled by the same kind of agent that is being judged. Related-need precision is 62.5%, and the three-way verdict is the stated differentiator.

Slice 3 groups and summarizes whatever the verdict produces. Building it on an unproven verdict would make errors look authoritative. The question this spec answers: _does the check before create actually prevent duplicates, judged against ground truth a person confirmed?_

## Solution

One proof run, with its bars set before it starts:

1. **A Pilot Workspace,** separate from the Crewday Demo Workspace, holding a generated pre-pilot backlog and an Answer Key of which feedback items share a need. The backlog, its expected duplicate rate and the Answer Key are fixed before the pilot runs. A person confirms every Answer Key label; feedback is generated by a different model family than the judge.
2. **Agents file, people review.** Agents act for simulated customers over MCP, about 200 filings, each through a Check: Support, Comment, or create with a Skip Reason. One or two people act as Product Managers: they review the scanned backlog for the baseline, then the new Feature Requests, with part of the reviews done without seeing the AI's suggestion.
3. **Clean counting.** Every Check and event records its Origin (pilot, demo, seed, eval); metrics are read per Origin. Eval runs and demo traffic never touch pilot numbers.
4. **A Held-Out Set v2** with at least 60 same-need positives spread across targets, written without sight of the current prompt, labels confirmed by a person, frozen before its first run. Readings show a 95% interval beside the point estimate.
5. **A Proof Report** that states, against the preset bars, pass or fail for each: Intake Duplicate Rate versus baseline, Review Coverage, agent correctness against the Answer Key, same-need precision (kill line) and related-need precision (three-way threshold).

## Definitions (from decision 0003)

| Term              | Meaning                                                                                                                                     |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Pilot Workspace   | A Workspace for the proof run, separate from the Crewday Demo Workspace; not open without a key.                                            |
| Answer Key        | For each pilot feedback item, the existing Feature Request it shares a need with (or none), confirmed by a person before the run.           |
| Origin            | Where a Check or event came from: `pilot`, `demo`, `seed` or `eval`. Recorded at the source, never inferred later.                          |
| Held-Out Set v2   | The second frozen Held-Out Set; v1 stays frozen as the first reading.                                                                       |
| Agent correctness | Share of agent Supports and creates that match the Answer Key. A Support on a request the Answer Key says is a different need is harm.      |
| Blind review      | A Review Decision made without seeing the AI's suggestion; used to measure Product Manager agreement with the Answer Key free of anchoring. |

**Preset bars** (decision 0003): pilot Intake Duplicate Rate ≤ ½ the backlog baseline; Review Coverage ≥ 80% over about 200 filings; same-need precision ≥ 85% on v2 (kill line, unchanged); related-need precision ≥ 75% on v2 keeps the three-way verdict.

## User Stories

1. As a Product Manager, I want the pilot's metrics separate from demo, seed and eval activity, so that a number I report is one I can defend.
2. As a Product Manager, I want the baseline backlog and its expected rate fixed before the pilot, so that nobody can say the comparison was built to look good.
3. As a Product Manager, I want to review some requests without seeing the AI's suggestion, so that my decisions measure the requests, not my agreement with the AI.
4. As an agent filing for a customer, I want the Check, Support and create to work the same in the Pilot Workspace as in the demo, so that the pilot tests the real journey.
5. As the founder, I want a Proof Report that says pass or fail against bars written before the run, so that the slice-3 decision isn't argued after the fact.
6. As the founder, I want same-need and related-need precision on human-confirmed labels with intervals, so that the kill line and the three-way claim rest on evidence a skeptic accepts.
7. Failure: a pilot request without the Pilot Key is refused, and demo traffic never lands in the Pilot Workspace.
8. Failure: changing the Answer Key or Held-Out Set v2 after it is frozen is visible (the reading resets and the report says so).

## Capabilities

Contracts are written contract-first during tasks; this section states what each must do and for whom.

- **Pilot Workspace:** created by an Operator with its backlog and Answer Key; Checks, Supports, Comments, creates, the Review Queue and metrics are scoped to it. The existing REST and MCP operations take the workspace through the caller's access, not a free-form parameter an agent can guess.
- **Origin:** every Check and event carries an Origin; metrics (REST, MCP and `/review`) accept an Origin and default to the caller's own. Existing demo rows backfill as `demo` or `seed`; eval runs record `eval`.
- **Blind review:** the Review Queue can withhold the AI suggestion and Reason for a request chosen for blind review; the decision records that it was blind.
- **Answer Key scoring:** agent correctness and Product Manager agreement (blind and not) are computed against the Answer Key for the Pilot Workspace.
- **Held-Out Set v2 and eval readings:** the eval runs v2 once per prompt version, logs every run with its prompt version, and reports point estimates with 95% intervals for same-need and related-need precision. Eval Checks never count in pilot or demo metrics.
- **Proof Report:** one read-only view (REST, MCP and a page) of every bar, its value, counts, interval where it applies, and pass or fail.

**MCP:** agents use the existing tools (`check_feature_request`, `support_feature_request`, `comment_on_feature_request`, `create_feature_request`, `get_feature_request`) unchanged in shape; the Pilot Key selects the Pilot Workspace. A read tool for the Proof Report is added. Errors an agent can act on: missing or wrong Pilot Key (refused, says which), frozen set changed (reading reset).

**Exposure:** the Crewday demo stays as it is (open reads, Operator-gated review writes). The Pilot Workspace is reachable only with a Pilot Key over REST and MCP, and with Operator access in the UI; without the key configured, every pilot read and write fails closed. Proof Report reads require the Pilot Key or Operator access.

## Testing Decisions

Test-first, as in specs 001 and 002, with the judge mocked: Origin recorded on every Check and event and respected by every metric; Pilot Key refusal and fail-closed behavior; workspace isolation (no demo row or metric leaks into the pilot and back); blind review withholding the suggestion and recording blindness; Answer Key scoring, including harm for wrong Supports; interval math; freeze detection for the Answer Key and Held-Out Set v2; REST/MCP parity rows for new operations. Metric-definition examples in `lib/signal/service/metric-definitions.test.ts` gain agent correctness and the Origin rule. Model quality is measured by the v2 reading, not unit tests.

**Acceptance scenario (founder and Product Manager, branch preview).** Steps assert behavior and bars, not specific AI outputs.

1. Starting state: a preview with its own database branch; the Crewday Demo Workspace as today; a Pilot Workspace with a generated backlog, its expected duplicate rate and a person-confirmed Answer Key, all frozen. Pilot metrics show zero, with counts.
2. Without the Pilot Key, pilot reads and writes are refused; demo pages behave as before.
3. The Product Manager runs the backlog scan in the Pilot Workspace and reviews it to at least 80% coverage; the backlog baseline appears with counts. Demo metrics are unchanged.
4. Agents file about 200 feedback items through Checks over MCP with the Pilot Key. Pilot Checks appear only in pilot metrics.
5. The Product Manager reviews new Feature Requests to at least 80% coverage, some blind. Intake Duplicate Rate, Review Coverage, agent correctness and Product Manager agreement (blind and not) show with counts.
6. The eval runs Held-Out Set v2 once; its Checks count only as `eval`. Same-need and related-need precision show with 95% intervals.
7. The Proof Report shows each bar with pass or fail. If same-need precision is below 85%, it states the kill criterion is triggered; if related-need precision is below 75%, it states the three-way verdict is to be narrowed.

**Acceptance scenario (agent, MCP):** with the Pilot Key, an agent checks a draft, gets a Verdict with Reason, supports an existing request, then reads the Proof Report; without the key, both are refused with an actionable error.

## Out of Scope

Real customers, customer sign-in or portals, external sign-in beyond the Pilot Key, tracker integrations, slice 2's remaining UI and slice 3 (underlying-need grouping, evidence summaries). Prompt or retrieval tuning beyond what v2 readings require. Changing the Held-Out Set v1 or decision 0002's metric definitions.

## Assumptions and risks

- **Human labeling time** (about 2–3 hours for v2 and the Answer Key) is available and done by someone other than whoever writes the pilot backlog. Open: who.
- **Pilot domain:** assumed workforce scheduling like Crewday but with new customers and a new backlog, so no pilot target reuses a Crewday seed request. Open.
- **Agents obey the verdict.** Mitigated by scoring correctness against the Answer Key; acceptance is not evidence.
- **Reviewer anchoring.** Mitigated by blind review and reporting agreement with the Answer Key separately.
- **Small samples.** About 200 filings and at least 60 positives are minimums; if an interval straddles a bar, the report says inconclusive rather than pass.
- **Goodhart on 85%.** v2 is frozen before any run and run once per prompt version, with every run logged.
- **Cost:** about 200 pilot Checks plus v2 readings and one backlog scan; within existing AI Gateway limits (assumption).
